# 02 읽기와 유형 정하기

Codex가 PLAN을 쓰는 동안 나도 README를 직접 읽는다. Codex 요약만 믿지 않는다.
읽으면서 "담당자에게 물을 것"이 떠오르면 notes/memo.md에 메모해 둔다.

## 할 일

1. README를 처음부터 끝까지 한 번. 이런 문장에 눈을 둔다
   - "반드시, 필수, ~해야, 하지 마세요, 수정 금지, 제외"
   - 숫자 조건, 표, 양식 블록, 예시 출력
   - 다른 파일을 가리키는 말 (그 파일도 과제 문서다)
2. notes/PLAN.md와 대조. 빠진 요구가 있으면
   `README의 "(문장)"이 PLAN 필수 요구에 없어. 추가하고 확인 방법도 붙여줘`
3. notes/deliverables.txt가 README의 제출물과 맞는지 본다. 양식이 정해진 문서는 지금 빈 양식 파일을 만들어 둔다
   `제출물 중 양식이 정해진 문서를 양식 그대로 빈 파일로 만들어줘. 이미 있는 파일은 건드리지 마`
4. 유형을 정한다. 1분 넘게 고민되면 build

| 과제가 이렇게 말하면 | 유형 | 06 파일 |
| --- | --- | --- |
| 시작 코드 없음, 서비스·기능을 새로 개발 | 새로 만들기 | 06_build.md |
| 이미 있는 코드가 틀리게 동작, 버그, 테스트 실패 | 고치기 | 06_fix.md |
| 돌아가는 코드에 기능 추가, 요구 변경 | 기존 코드 확장 | 06_extend.md |
| 데이터로 질문에 답하기, 보고서, 지표 | 분석·리포트 | 06_data.md |
| 느림, 죽음, 에러율, 장애 원인 | 성능·장애 | 06_incident.md |
| 설계안, 계획서, 검토 문서가 주 산출물 | 설계·문서 | 06_design.md |

섞여 있으면 산출물의 대부분을 차지하는 쪽. 나머지 유형의 철칙은 해당 단위에서만 06 파일을 잠깐 연다.

5. 과제 성격도 하나 고른다: ref/patterns.md (배치·편성, 추천, 규칙·심사, 분석, 품질 데이터, 안내·질의응답, 화면 프로토타입). 그 절의 "먼저 물을 것" 중 README가 이미 답한 것은 빼고 ASK.md에 더한다

## 끝 기준

- 유형과 06 파일을 정했다
- PLAN의 필수 요구, 제외 범위, 제출물이 README와 맞는다
- 커밋: Codex에 `PLAN 정리한 것 커밋 메시지 추천해줘` → ok

점수 연결: 목표와 제약을 명확히 정의 (의도)
