# 05 결정과 작업 단위 · 끝 19:42

설계를 혼자 짜지 않는다. Codex가 선택지를 주고, 나는 고르고, 이유를 말한다. 그게 결정 카드로 남는다.

## 할 일

1. Codex에
   ```text
   PLAN의 "내가 정해야 할 결정"을 AGENTS.md 형식으로 물어봐. 서로 독립된 건 한 번에 묶어서.
   첫 번째는 스택과 실행 방식이야. 이미 코드가 있으면 그 스택 유지 여부부터.
   지금 안 정해도 구현을 시작할 수 있는 결정은 뒤로 미뤄. 정해진 건 결정 카드로.
   ```
   급하면 "추천대로"라고 답해도 된다. Codex가 이유를 선택지로 다시 묻고, 내가 고른 이유로 결정 카드가 남는다
   핵심 로직이 어려워 보이면(정답이 하나가 아닌 계산, 여러 조건) 이어서 ref/algorithm.md의 "쪼개기와 후보 받기"를 보낸다. 하위 문제마다 기준선과 개선 후보 중에서 고른다
2. 고를 때 내 기준 (스택이면 ref/stacks.md도 참고)
   - 요구사항을 직접 만족하나 (DB, 컨테이너, 화면, 역할 같은 실행 조건 포함)
   - 3시간 안에 만들고 검증까지 할 수 있나
   - 내가 흐름을 설명할 수 있나
   - 틀리면 되돌리기 쉬운가
3. 결정이 끝나면 작업 단위
   ```text
   정한 내용으로 PLAN에 작업 단위 4~8개를 써줘. 단위마다 관련 R 번호, 목표, 바꿀 파일, 완료 기준(눈으로 볼 수 있는 결과), 검증 위치(tests/ 또는 checks/). 모든 R이 어느 단위엔가 들어가야 해.
   순서: 끝까지 도는 가장 작은 흐름을 먼저, 그다음 넓히기. 첫 단위는 (아래 표의 첫 단위)로. 핵심 로직이 있으면 검증기 → 기준선 → 개선 순서로 단위를 나눠.
   ```

| 유형 | 첫 단위 |
| --- | --- |
| build | 실행 뼈대: 서버 기동, 상태 확인, 저장소 연결, 과제가 요구한 실행 조건 |
| fix | 버그를 재현하는 실패 테스트 |
| extend | 기존 코드 실행과 기존 테스트 통과 확인, 기준점 커밋 |
| data | 데이터 읽기와 핵심 숫자 하나를 재현 가능한 스크립트로 |
| incident | 문제 재현과 기준 측정값 |
| design | 산출 문서 목차와 요구→설계 추적표 |

4. Codex가 단위를 쓰는 동안: 담당자 답이 왔는지 보고 반영 지시. 다 쓰면 순서와 범위를 내가 본다. 빠진 필수 요구, 요구에 없는 단위가 있으면 말로 고친다
5. 커밋 (추천 메시지 → ok)

## 끝 기준

- 결정 카드 1개 이상 (최소한 스택)
- PLAN에 작업 단위 목록과 단위별 완료 기준

점수 연결: 작업을 나누고 AI에 위임 (의도), 구조를 선택한 이유 (인지)
