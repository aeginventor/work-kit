# 06 새로 만들기 · 20:30 핵심 흐름 1개 완성 · 21:15 새 기능 중단

## 철칙

1. 끝까지 도는 가장 작은 흐름 하나를 먼저 완성한다 (입력 → 처리 → 저장 → 화면·출력). 화면 꾸미기, 부가 기능은 그다음
2. 과제가 요구한 실행 조건(설정 방식, 저장소, 상태 확인, 컨테이너, 인증 등)은 첫 뼈대에 넣는다. 후반에 처음 발견하면 시간이 없다 (ref/deploy.md)
3. 과제가 결과 형식이나 규칙을 문서로 정했으면, 그 규칙을 검사하는 검증을 생성 로직보다 먼저 checks/에 만든다. 문서만 보고 만들게 한다 (구현 코드를 보고 만든 검증은 같은 실수를 공유한다)
4. 결과를 저장할 때 "어떤 입력과 설정으로 만든 결과인지"를 같이 남긴다. 입력이 바뀔 수 있는 서비스라면 지금 보여주는 결과가 최신 입력 기준인지 판단할 근거가 된다
5. 핵심 로직이 어려우면 화면보다 로직이 먼저다: 검증기 → 기준선(규칙만 지키는 단순한 방법) → 제출 가능 상태 커밋 → 개선 (ref/algorithm.md). 화면은 금방 되지만 로직은 시간이 걸린다
6. 화면 중심 프로토타입(게임, 시뮬레이션)이면: 핵심 상호작용 하나 먼저, 규칙 로직은 화면 코드와 분리해 테스트, 난수는 고정 시드

기본 지시 틀 (첫 단위, 위험한 단위)
```text
(기능 하나)를 만들어줘. (요구 계약, 기존 구조)는 지켜.
시작 전에 바꿀 파일과 방법, 확인 방법을 알려주고 기다려.
끝나면 정상 경로와 실패 경로를 실제로 실행해서 결과를 보여줘.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기: 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 설명 카드의 "깨지면" 한 줄과 예상 질문을 30초 읽는다. 납득이 안 될 때만 `쉽게 설명해줘`
   - "요구에 없는데 넣은 것"이 있으면 빼거나 이유를 듣고 남긴다
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄
