# 06 분석·리포트 · 20:30 핵심 질문의 숫자 완성 · 21:15 새 분석 중단

## 철칙

1. 질문을 숫자로 정의한다. 무엇을 셀지(분자), 무엇 대비인지(분모), 기간, 대상, 제외 조건. 애매하면 담당자에게
2. 원본 데이터는 수정하지 않는다. 모든 숫자는 다시 돌릴 수 있는 스크립트(scripts/)에서 나온다. 손으로 고친 숫자 금지
3. 작은 범위로 손계산 대조. 하루, 한 그룹처럼 사람이 셀 수 있는 크기에서 스크립트 결과와 맞춰 본다 (그 대조를 checks/에)
4. 관측한 것과 추정한 것을 구분해서 쓴다. 데이터에 없는 원인, 개인 의도, 기록되지 않은 경우를 단정하지 않는다

기본 지시 틀
```text
(질문)에 답할 숫자를 만들어줘. 원본 데이터는 수정하지 마.
시작 전에 계산 정의(분자, 분모, 기간, 제외 조건)와 가정을 알려주고 기다려.
결과는 scripts/의 스크립트와 실제 출력으로 보여주고, 작은 범위 손계산 대조도 같이.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기: 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 설명 카드의 "깨지면" 한 줄과 예상 질문을 30초 읽는다. 납득이 안 될 때만 `쉽게 설명해줘`
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄

## 흔한 함정

- 반복 기재된 합계를 행마다 더하기, 기준일과 실제 일시 섞기 (notes/DATA.md 함정 점검)
- 평균만 보기 → 분포(최대, 상위 몇 %)와 예외 그룹도 본다
- 그래프·표를 먼저 꾸미기 → 숫자가 맞는지가 먼저

## 산출물

- 결과 문서: 질문 → 답(숫자) → 계산 방법 → 한계와 가정. 과제가 양식을 주면 그 양식
- 재현 명령: `python3 scripts/○○.py` 한 줄로 같은 숫자가 나와야 한다
