# 06 설계·문서 중심 · 남음 1:30 목차 전체 초안 · 남음 0:45 새 절 추가 중단

## 철칙

1. 산출물은 문서다. 과제가 준 양식과 목차를 그대로 따르고 먼저 전체 뼈대(제목들)를 만든다
2. 요구 → 설계 요소 추적표를 만든다. 모든 필수 요구가 어느 절에서 다뤄지는지 보인다
3. 중요한 설계마다 대안 비교와 고른 이유, 감수한 한계를 쓴다 (결정 카드를 그대로 옮기면 된다)
4. 핵심 가정 하나는 작은 스크립트나 계산으로 확인한다. 말뿐인 설계보다 근거가 생긴다

기본 지시 틀
```text
(절 이름)을 써줘. PLAN의 요구 (번호)를 다뤄야 해.
쓰기 전에 다룰 요구, 비교할 대안, 근거로 쓸 데이터나 계산을 먼저 알려주고 기다려.
내가 고르지 않은 결정을 확정된 것처럼 쓰지 말고, 근거 없는 수치는 "가정"으로 표시해.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기 (화면이 안 돌아오면 `q`): 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 설명 카드의 "깨지면" 한 줄과 예상 질문을 30초 읽는다. 납득이 안 될 때만 `쉽게 설명해줘`
   - "요구에 없는데 넣은 것"이 있으면 빼거나 이유를 듣고 남긴다
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄
