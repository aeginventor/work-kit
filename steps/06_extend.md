# 06 기존 코드 확장 · 20:30 첫 기능 완성 · 21:15 새 기능 중단

## 철칙

1. 기존 코드부터 돌린다. 실행 명령, 테스트 명령, 기존 테스트 결과를 확인하고 그 상태를 기준점으로 커밋한다
2. 기능 하나가 코드 안에서 어떻게 흐르는지 먼저 본다. `(기존 기능 하나)가 요청부터 저장까지 어떤 파일·함수를 거치는지 순서대로` 
3. 기존 구조와 스타일을 따른다. 같은 로직을 복사하지 말고 있는 걸 재사용한다. 새 의존성은 결정 카드로
4. 새 기능마다 기존 기능이 그대로인지(회귀) 확인한다. 기존 테스트는 지우거나 바꾸지 않는다

기본 지시 틀
```text
(새 기능)을 추가해줘. (기존 계약·구조)는 유지해.
시작 전에 바꿀 파일과 기존 코드 중 재사용할 부분을 알려주고 기다려.
끝나면 새 기능의 정상·실패 경로와 기존 테스트 전체를 돌려서 결과를 보여줘.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기: 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 설명 카드의 "깨지면" 한 줄과 예상 질문을 30초 읽는다. 납득이 안 될 때만 `쉽게 설명해줘`
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄

## 흔한 함정

- 기존 코드를 다 읽히기 → 진입점과 관련 파일만
- 기존 테스트가 원래 실패하던 걸 내 탓으로 착각 → 기준점 커밋 때 실패 목록을 PLAN에 적어 둔다
- 요구가 바뀐 부분과 그대로인 부분을 섞기 → PLAN에 "바뀌는 것 / 유지할 것"을 나눠 적는다
