# 06 고치기 · 20:30 원인 확정과 첫 수정 · 21:15 새 수정 중단

## 철칙

1. 재현 먼저. 버그를 실패하는 테스트로 고정한 뒤에 고친다. 재현 못 하면 고친 걸 증명할 수 없다
2. 원인 먼저, 수정은 나중. 원인과 변경 범위(파일, 함수)를 보고받고 내가 승인한다
3. 기존 계약은 유지한다. API 경로, 응답 형식, 저장 데이터 형식은 과제가 바꾸라고 하지 않는 한 그대로
4. 수정 후 같은 테스트 + 관련 정상 경로 + 실패 경로를 다시 돌린다. 테스트를 고쳐서 통과시키지 않는다

기본 지시 틀 (공식 예시 형태)
```text
(증상)의 원인을 먼저 찾아줘. (유지할 것)은 바꾸지 마.
수정 전에 원인 근거(코드 위치)와 변경 범위를 알려주고 기다려.
수정 후 같은 테스트로 다시 확인하고, 실패 상황도 테스트해서 결과를 보여줘.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기: 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 이해 확인 질문에 한 줄로 답하기 (막히면 `쉽게 설명해줘`). 이게 서술형 연습이다
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄
