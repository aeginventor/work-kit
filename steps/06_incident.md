# 06 성능·장애 대응 · 남음 1:30 원인 확정 · 남음 0:45 새 변경 중단

## 철칙

1. 측정 먼저. 재현 조건과 기준 수치(응답 시간, 에러율, 처리량, 메모리, 로그 패턴)를 먼저 잡는다. 숫자 없이 "빨라졌다"는 증명이 안 된다
2. 가설은 하나씩, 변경도 한 번에 하나. 같은 측정으로 전후를 비교한다
3. 임시 조치와 근본 원인을 나눠서 기록한다. 시간 안에 근본 원인을 못 고치면 그 사실을 쓴다
4. 동작 계약은 유지한다. 빨라졌지만 결과가 달라지면 실패다. 로그에 비밀값을 찍지 않는다

기본 지시 틀
```text
(증상)의 원인을 측정으로 먼저 찾아줘. (유지할 동작)은 바꾸지 마.
재현 방법과 기준 측정값, 원인 근거(로그·코드 위치)와 변경 범위를 먼저 알려주고 기다려.
수정 후 같은 측정을 다시 돌려 전후 숫자를 비교하고, 기존 테스트도 돌려줘.
```

## 단위 루프 (작업 단위마다 반복)

1. Codex에 `PLAN 단위 n 진행해` (첫 단위, 위험한 단위는 계획 보고를 먼저 받고 ok)
2. 기다리는 동안: 담당자 답 확인(04), 터미널 2에서 직접 실행해 보기, 다음 단위 생각
3. 보고가 오면
   - 터미널 2에서 `git diff --stat` → `git diff` 훑기 (화면이 안 돌아오면 `q`): 예상한 파일만 바뀌었나, 요구에 없는 게 끼었나
   - "추가한 검증" 줄의 기대값이 요구·담당자 답과 맞나 (코드 말고 문장만 판단)
   - 설명 카드의 "깨지면" 한 줄과 예상 질문을 30초 읽는다. 납득이 안 될 때만 `쉽게 설명해줘`
   - "요구에 없는데 넣은 것"이 있으면 빼거나 이유를 듣고 남긴다
   - 커밋 메시지 ok 또는 고쳐서 답하기
4. 틀렸으면 처음부터 다시 시키지 않는다: `(파일)의 (부분)이 틀렸어. 이유는 (이유). 그 부분만 고쳐`
5. 설명이 이해 안 되면 커밋 전에: `방금 바꾼 (함수)가 어떤 순서로 도는지 쉬운 말로 5줄`
6. 계획을 바꿔야 하면 PLAN 단위를 고치고 DECISIONS "방향 조정"에 한 줄

## 흔한 함정

- 로그·설정을 통째로 읽히기 → 에러 줄과 시각 주변만 (`grep`, `tail -100`)
- 여러 개를 한꺼번에 바꾸기 → 무엇이 효과였는지 설명 못 함
- 환경 문제(포트, 권한, 컨테이너 재시작으로 바뀐 주소)를 코드 버그로 착각 → 앱, 주소, 도구, 환경으로 나눠서 확인
